# Git Convention

이 문서는 프로젝트의 Git 작업 기준을 정의한다.

Git은 단순 버전 관리 도구가 아니라,
작업 흐름과 변경 의도를 기록하는 수단으로 본다.

---

## 핵심 방향

- 작은 단위로 자주 커밋한다.
- 커밋 하나는 하나의 의도를 가진다.
- 변경 이유를 추적 가능해야 한다.
- 기능 단위로 PR을 구성한다.
- 리뷰 가능한 크기를 유지한다.

---

## 커밋 단위

커밋은 가능한 작은 단위로 나눈다.

기능 구현 커밋은 기대 행위 단위로 나누고,
기본 순서는 테스트 커밋 → 구현 커밋이다.

좋은 예시:

- 메서드 하나 리팩토링
- 테스트 추가
- 예외 구조 수정
- 네이밍 수정
- 기대 행위 하나를 표현하는 테스트 커밋
- 해당 테스트를 통과시키는 구현 커밋

지양하는 예시:

- 여러 기능 한 번에 커밋
- 구조 변경 + 기능 추가 혼합
- 테스트와 기능 수정이 무작위로 섞임

---

## 커밋 메시지

Conventional Commits 스타일을 사용한다.

### 형식

    type: summary

### 예시

    feat: 주문 취소 기능 추가
    refactor: 검증 책임을 policy로 분리
    fix: 중복 검증 누락 수정
    test: 주문 생성 테스트 추가

---

## 커밋 타입

### feat

새 기능 추가

### fix

버그 수정

### refactor

동작 변경 없는 구조 개선

### test

테스트 추가 및 수정

### docs

문서 수정

### chore

설정, 빌드, 기타 작업

---

## 브랜치 전략

브랜치는 작업 목적 단위로 생성한다.

좋은 예시:

    feat/order-cancel
    refactor/validator-separation
    fix/duplicate-validation

지양하는 예시:

    test
    temp
    final-final-real

---

## Pull Request 기준

PR은 기능 단위로 올린다.

### 좋은 기준

- 하나의 사용자 시나리오
- 하나의 책임 변경
- 리뷰 가능한 크기

### 지양하는 기준

- 여러 기능 혼합
- 대규모 구조 변경 한 번에 포함
- 의도를 설명하기 어려운 변경

---

## PR 설명

PR에는 아래 내용을 포함한다.

- 무엇을 변경했는가
- 왜 변경했는가
- 어떤 기준으로 설계했는가
- 리뷰 시 중점적으로 볼 부분은 무엇인가

---

## 리팩토링 커밋

리팩토링은 가능한 기능 변경과 분리한다.

좋은 예시:

    refactor: policy 객체 분리
    feat: 주문 취소 기능 추가

지양하는 예시:

    feat: 주문 취소 및 전체 구조 수정

---

## 테스트 커밋

테스트 추가는 가능한 명확히 드러낸다.

테스트 커밋은 기대 행위나 실패 케이스를 먼저 표현한다.
이후 구현 커밋은 그 테스트를 통과시키는 변경만 포함한다.

좋은 예시:

    test: 주문 취소 실패 케이스 추가
    feat: 주문 취소 실패 케이스 처리

---

## 지양하는 방식

- 의미 없는 대규모 커밋
- 변경 이유 없는 force push 반복
- 테스트 없이 기능만 추가
- "최종", "진짜최종" 같은 브랜치 이름
- 동작 변경과 리팩토링을 한 커밋에 혼합

---

## 판단 기준

커밋과 PR 구성이 헷갈리면 아래 질문으로 판단한다.

- 변경 이유를 한 문장으로 설명 가능한가?
- 리뷰어가 흐름을 따라가기 쉬운가?
- 되돌려야 할 때 영향 범위를 예측 가능한가?
- 기능과 구조 변경이 자연스럽게 분리되어 있는가?

YES라면 좋은 Git 단위 가능성이 높다.
