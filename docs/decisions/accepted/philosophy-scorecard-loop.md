# Philosophy Scorecard Loop

## 상태

accepted

---

## 문제 상황

docs의 철학이 코드에서 실제로 지켜지는지 측정 수단이 없었다.

- 지침 준수가 Review의 승인 / 반려라는 이진 판정으로만 남아,
  어떤 철학이 자주 약해지는지 보이지 않는다.
- 프롬프트(카드 지침, 역할 docs)의 개선 방향을 감으로 정하게 된다.

코드라는 산출물이 카드마다 남으므로, 그것을 근거로 철학 준수를
정량화할 수 있다.

---

## 선택한 방향

철학을 점수표로 변환하고, 채점 → 집계 → 개선의 루프를 돈다.

- 점수표 항목의 정본은 `templates/06-scorecard.md`다.
  각 항목은 docs의 철학 / decision에서 도출되고 출처를 가리킨다.
- Review Agent가 카드마다 채점한다. 점수는 0 / 1 / 2 / N/A이고
  근거에 코드 위치를 인용한다.
- 완료된 점수표는 history에 누적되고,
  `scripts/loop/aggregate-scores.sh`가 항목별 평균과 감점 카드를 집계한다.
- 낮은 항목은 /loop-improve가 원인(지침 부족 / 지침 위반)을 진단하고
  프롬프트 개선을 제안한다. 반영은 사람 승인 후에만 한다.

절차의 정본: [loop-engineering](../../workflow/loop-engineering.md)

---

## 선택 이유

### 산출물 기반 정량화

코드와 diff가 카드마다 남으므로 채점의 근거가 항상 존재한다.
인상 평가가 아니라 코드 위치를 인용하는 채점이 가능하다.

### 낮은 점수 = 프롬프트 결함 신호

같은 항목이 반복해서 감점되면 작업자가 아니라 지침이 용의자다.
점수가 어느 문서를 고칠지 가리킨다.

### 개선 효과의 측정 가능성

제안마다 기대 효과를 명시하고 다음 집계로 검증하므로,
프롬프트 개선이 일회성 수선이 아니라 닫힌 루프가 된다.

---

## 트레이드오프

### 채점 비용

Review 단계가 판정에 더해 14개 항목을 채점한다.
근거 인용을 요구해 형식적 채점을 억제하지만 비용은 남는다.

### 점수 형식화 위험

근거 없는 만점이 반복되면 통계가 무의미해진다.
전 항목 만점 고착은 항목이 무뎌진 신호로 본다.

---

## 현재 판단

채점은 Review의 표준 출력으로 강제하고,
집계와 개선 제안은 백로그 완료 시점의 운영 절차로 둔다.

점수표 항목의 변경은 draft decision을 거치고 변경 시점을 기록해
이전 통계와의 비교 가능성 단절을 관리한다.

---

## 재검토 신호

- 점수에 코드 위치 근거가 없는 채점이 반복된다.
- 전 항목 만점이 고착된다 (항목이 무뎌짐).
- N/A가 항상 많은 항목이 있다 (항목 또는 카드 분해 문제).
- 개선 반영 후에도 같은 항목 평균이 오르지 않는다 (진단 오류).
- 채점 비용이 Review 판정 자체를 부실하게 만든다.
