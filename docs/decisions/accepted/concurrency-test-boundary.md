# Concurrency Test Boundary

## 상태

accepted

---

## 문제 상황

동시성 위험이 있는 유스케이스를 일반 Service 단위 테스트로 검증할 수 있는지 결정이 필요했다.

---

## 선택한 방향

동시성 테스트는 실제 Spring Context와 DB를 사용하는 통합 테스트로 작성한다.

일반 Service 단위 테스트를 대체하지 않는다.

---

## 선택 이유

### 실제 실행 환경 필요

동시성 문제는 Mock/Fake만으로 검증하기 어렵다.

아래 요소가 함께 동작한 결과를 봐야 한다.

- 트랜잭션
- DB lock
- unique constraint
- Repository 구현
- 실제 실행 순서 경쟁

---

### Service 테스트와 목적이 다르다

Service 테스트는 orchestration을 검증한다.

동시성 테스트는 동시에 요청 또는 유스케이스를 실행했을 때
최종 상태가 요구사항과 맞는지 검증한다.

---

## 작성 기준

동시성 위험이 요구사항이나 코드 구조상 명확할 때 작성한다.

예시:

- 동일 주문 중복 생성
- 재고 차감
- 결제 승인
- 대기 순번
- 주문 취소와 결제 승인이 동시에 발생하는 흐름

---

## 트레이드오프

### 테스트 비용 증가

Spring Context와 DB를 사용하므로 느리고 무겁다.

---

### 재현 안정성 관리 필요

동시성 테스트는 실행 타이밍에 민감할 수 있다.

`CountDownLatch`, thread pool, 명확한 최종 상태 검증 등으로 재현 가능성을 높인다.

---

## 현재 판단

동시성 테스트는 단위 테스트가 아니라 실제 실행 환경을 사용하는 통합 테스트다.

이 원칙이 모든 Service 테스트를 `@SpringBootTest`로 작성하는 근거가 되어서는 안 된다.

---

## 재검토 신호

- 동시성 위험이 없는 유스케이스까지 통합 테스트로 작성한다.
- Mock/Fake 테스트로 DB lock이나 race condition을 검증했다고 판단한다.
- 최종 상태가 아니라 호출 여부만 검증한다.
- 테스트가 간헐적으로 실패하고 원인을 추적할 수 없다.
