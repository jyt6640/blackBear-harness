# Agent Handoff By Artifact

## 상태

accepted

---

## 문제 상황

기능 하나를 테스트 → 기능 개발 → 리뷰 단계로 나눠 진행할 때,
단계 간 맥락 전달을 채팅 메모리에 의존하면 두 가지 문제가 생긴다.

- 채팅 메모리는 한계가 있어 맥락이 유실된다.
- 단계마다 모델이 달라지면(Claude / 로컬 LLM 교체) 맥락이 끊긴다.

---

## 선택한 방향

각 단계는 md 산출물을 무조건 남긴다.
다음 단계는 이전 산출물만 읽고 시작할 수 있어야 한다.

산출물이 단계 간 인터페이스다.
채팅 기억에 의존하는 핸드오프를 금지한다.

### 산출물 체인

작업(기능) 단위로 아래 위치에 쌓는다.

    next-step/work/<작업명>/
    ├── 00-task-card.md          (오케스트레이터 또는 사용자: 작업 정의)
    ├── 01-test-report.md        (Test Agent: 실패 테스트 작성 결과)
    ├── 02-implementation-report.md (Feat Agent: 구현 결과)
    │   (refactor 카드는 02-refactor-report.md — 01 없이 진행 가능)
    ├── 03-review-report.md      (Review Agent: 승인 / 반려)
    └── 04-summary.md            (오케스트레이터: 통합 보고)

### 순서 강제

이전 단계의 산출물이 없으면 다음 단계를 시작하지 않는다.

- 단계 전환은 사용자의 스킬 호출로만 한다.
  각 단계는 끝나면 멈추고 다음 스킬 실행을 사용자에게 요청하며, 다음 단계를 직접 실행하지 않는다(사용자 릴레이).
- 각 역할 스킬과 enforce-workflow.sh가 이전 산출물 존재를 확인하고, 없으면 진행을 거부한다.
- 표준 릴레이는 /orchestrate → /test-agent → /feat-agent → /refactor-agent → /review-agent 순서다.
  feature 카드도 Refactor 단계를 건너뛰지 않는다. 개선할 것이 없으면 보고서에 "개선 사항 없음"과 행위 보존 확인을 기록한다.
- 오케스트레이션 모드(pending)에서는 오케스트레이터가 이 전환을 자동화한다.

산출물 존재는 기계 판정 가능하므로
프로젝트에서 스크립트로 강제할 수 있다.
→ [enforcement-by-script](./enforcement-by-script.md)

## 선택 이유

### 모델 독립성

단계의 입출력이 파일이므로,
어떤 단계의 모델을 갈아끼워도 개발 흐름에 차질이 없다.

### 맥락의 영속성

채팅이 끊기거나 세션이 바뀌어도
산출물 체인만 있으면 어느 단계에서든 이어서 진행할 수 있다.

### 진행 상태의 가시성

팀원과 사람이 산출물을 읽는 것만으로
어디까지 진행됐고 무엇이 결정됐는지 알 수 있다.

---

## 트레이드오프

### 산출물 작성 비용

단계마다 보고서를 쓰는 비용이 든다.
산출물은 다음 단계가 시작할 수 있는 최소 내용으로 유지하고,
형식적 문서가 되면 항목을 줄인다.

---

## 현재 판단

이 원칙은 단일 모드와 오케스트레이션 모드 모두에 적용된다.
각 에이전트의 산출물 필수 항목은 해당 에이전트 하네스가 정의한다.

---

## 재검토 신호

- 산출물이 형식적으로 채워지고 다음 단계가 코드를 다시 읽는다.
- 산출물 작성 비용이 단계 작업 자체보다 커진다.
- 같은 내용이 산출물과 커밋 메시지에 중복된다.
