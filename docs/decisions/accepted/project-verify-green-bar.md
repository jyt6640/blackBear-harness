# Project Verify Green Bar

## 상태

accepted

---

## 문제 상황

"되는 코드"의 정의가 암묵적이었다.

역할 에이전트(Feat / Refactor)가 각자 방식으로 테스트를 돌리고
Review가 확인했지만, 프로젝트에 "이 명령이 통과하면 된 것이다"라는
단일 기준 명령이 없었다.

로컬 LLM은 자기 판단으로 테스트를 골라 돌리므로 빠뜨릴 수 있고,
모델이 바뀌면 green-bar 해석도 흔들렸다.

---

## 선택한 방향

프로젝트 저장소 루트에 `verify.sh`를 둔다.

- build + test가 통과하면 exit 0, 아니면 비0.
- 이 프로젝트에서 "되는 코드"의 단일 기계적 정의다.
- 역할 에이전트와 백로그 루프는 이 한 명령으로 완료를 판정한다.
- 모델이 무엇이든(로컬 LLM / 강모델) 같은 자로 잰다.
- 템플릿: `scripts/project-templates/verify.sh` (프로젝트가 복사해 채운다).

Feat / Refactor 단계의 green-bar는 `verify.sh` 통과다.
Review는 `verify.sh` 결과를 산출물에서 확인하고, 통과하지 않으면 반려한다.

---

## 선택 이유

### 단일 진실

테스트를 "어떻게 돌렸는가"가 모델·역할마다 달라도,
`verify.sh` 하나가 통과 여부를 같은 자로 잰다.

### 게이트가 키로 삼을 토대

산출물 체인, 백로그 루프, 점수표가 모두 `verify.sh` green-bar를
완료 판정의 기준으로 삼는다. 깨진 코드가 산출물 체인에 들어가지 못한다.

---

## 트레이드오프

### 느린 verify

`verify.sh`가 전체 빌드를 돌리면 느릴 수 있다.
빠른 피드백용으로 테스트만 도는 경로를 프로젝트가 둘 수 있으나,
완료 판정의 기준은 전체 green-bar다.

---

## 현재 판단

프로젝트 하네스 생성 시 `verify.sh`를 만든다.
없으면 역할 에이전트는 완료를 판정할 단일 기준이 없으므로,
프로젝트 하네스 생성의 필수 산출물로 둔다.

---

## 재검토 신호

- `verify.sh`가 너무 느려 루프 전체가 지연된다.
- 역할마다 verify를 우회해 자기 방식으로 테스트한다.
- green-bar 통과인데 실제로는 깨진 코드가 통과한다 (verify 범위 부족).
