# Domain Reference Adapter

## 상태

accepted

---

## 문제 상황

다른 도메인과 협력할 때 상대 도메인의 Repository를 직접 참조할지,
중간 포트를 둘지 결정이 필요했다.

Repository는 Domain 객체의 저장 경계이지만,
다른 도메인의 Repository를 직접 참조하면 상대 도메인의 객체를 가져와 외부에서 판단하기 쉽다.

또한 도메인 간 패키지 순환참조가 생길 수 있다.

---

## 선택한 방향

도메인 간 협력은 Reference 포트와 Adapter로 표현한다.

- Reference 포트는 협력이 필요한 쪽 application 패키지에 둔다.
- Adapter는 실제 협력 수단을 가진 도메인의 application 패키지에 둔다.
- Application Service가 상대 도메인의 Repository를 직접 참조해 내부 상태를 판단하는 방식을 피한다.

---

## 선택 이유

### 협력 캡슐화

Reference 포트는 단순 순환참조 방지 장치가 아니다.

다른 도메인과의 협력을 Tell, Don't Ask 방식으로 표현하는 경계다.

---

### 객체 노출 방지

상대 도메인의 객체를 가져와 현재 Service가 내부 상태를 판단하면
도메인 책임이 흐려질 수 있다.

Reference 포트는 필요한 사실이나 행위만 노출한다.

---

## Reference 포트 종류

### 사실 확인

`exists...`, `is...` 등 boolean 반환이 자연스럽다.

사실 확인 결과를 바탕으로 어떤 ErrorCode를 던질지는 현재 Validator / Application 책임이다.

### 행위 요청

다른 도메인에 생성, 변경, 승격 같은 협력 행위를 요청할 수 있다.

행위 요청 중 실패가 발생하면 기본적으로 실패 규칙을 소유한 도메인의 ErrorCode를 사용한다.
다만 최종 사용자 응답 의미가 달라야 하면 호출 쪽에서 예외를 감싸거나 변환할 수 있다.

---

## 트레이드오프

### 클래스 수 증가

Reference 인터페이스와 Adapter가 늘어난다.

---

### 단순 조회에도 구조가 필요

단순한 존재 확인도 포트를 거치므로 처음에는 무겁게 보일 수 있다.

하지만 도메인 간 협력 경계를 명시하는 비용으로 본다.

---

## 현재 판단

다른 도메인과 협력할 때는 Repository 직접 참조보다 Reference 포트를 우선한다.

이는 DDD를 완전히 도입하기 위한 규칙이 아니라,
도메인 간 책임 침범과 순환참조를 줄이기 위한 백엔드 하네스 기준이다.

---

## 재검토 신호

- Reference Adapter가 단순 위임만 반복해 의미가 약해진다.
- 포트 이름이 Repository 메서드 복사에 그친다.
- Adapter가 비즈니스 판단을 새로 만들기 시작한다.
- 도메인 간 협력보다 구조 유지 비용이 더 커진다.
