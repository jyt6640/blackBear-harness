# Repository Exception Contract

pending

---

## 문제 상황

Repository 인터페이스 계약에 저장소 의미 예외를
어느 수준으로 드러낼지 결정이 필요하다.

선택지는 아래 세 가지다.

- 드러내지 않음: 호출자가 구현체를 열어봐야 어떤 예외가 오는지 안다.
- 주석으로 명시: 인터페이스 주석에 어떤 제약 위반 시 어떤 예외가 발생하는지 적는다.
- 계약으로 적극 노출: 예외가 비즈니스 흐름의 일부로 인터페이스 설계에 드러난다.

이 질문은 영속성 기술이 무엇이든 발생하며,
Spring 전제와 무관하다.

---

## 판단 기준

- 저장소 기술과 DB 제약이 비즈니스 흐름의 일부인가
- 기술 스택 고정성 ([spring-dao-exception-propagation](./spring-dao-exception-propagation.md)과 함께 결정)
- 호출자가 예외를 잡아 의미를 부여해야 하는 유스케이스가 얼마나 되는가

---

## 잠정 기준

기본은 인터페이스 주석 명시다.
저장소 의미 예외는 unchecked이므로 시그니처에 드러나지 않지만,
호출자가 구현체를 열어보지 않고도 무엇을 잡을지 알 수 있어야 한다.

DB 종속이 확정된 프로젝트라면 계약에 적극 노출할 수 있다.
DB 제약이 비즈니스 흐름의 일부가 되기 때문이다.

---

## 프로젝트 결정 시점

프로젝트 하네스 생성 시
저장소 기술 고정 여부(상위 전제)와 함께 결정한다.

---

## 재검토 신호

- 인터페이스 계약과 실제 던지는 예외가 어긋난다.
- 호출자가 구현체 코드를 열어봐야 예외 처리를 작성할 수 있다.
- 예외 명시가 형식적 주석으로만 남고 유지되지 않는다.
