## 문제 상황

상위 오케스트레이션 모델(Claude)이 로컬 LLM 서브에이전트들에게
코드 작성을 위임하는 구조를 도입할지 결정이 필요하다.

목표 구조:

- 오케스트레이터가 서브에이전트의 하네스를 만들어 건넨다.
- 작업을 잘게 쪼개 로컬 LLM에게 위임해 토큰을 절약한다.
- 서브에이전트가 2개 이상이면 상호작용으로 결과 품질을 높인다.
- 오케스트레이터가 결과를 확인한 뒤 사용자에게 전달한다.

## 현재 방향

도입 시점은 미정이다.

서브에이전트 사용 여부는 사용자에게 질문해서 정한다.
사용하지 않으면 이 구조는 필요 없고,
사용하기로 할 때 아래 잠정 기준으로 시작한다.

## 잠정 기준 (도입 시)

### 하네스 분리

- `orchestrator/` 패키지에 오케스트레이션 하네스를 둔다. (backend-orchestrator 작성됨)
- `sub-agent/` 패키지에 역할별 하네스를 둔다. (backend-test-agent, backend-feat-agent, backend-review-agent 작성됨)
- 오케스트레이터는 일을 내리는 팀장 역할만 한다. 내용 검토는 Review Agent에 위임한다.
- 현재 base 하네스의 docs는 각 에이전트가 역할별 범위만 읽는 공유 정본이다.
- harness-interview와 how-to-create-project-harness는 오케스트레이터 책임으로 이동한다.

### 단계 간 핸드오프

- 모든 단계는 md 산출물을 남기고, 산출물이 단계 간 인터페이스다.
  → [agent-handoff-by-artifact](../accepted/agent-handoff-by-artifact.md)
- 이 원칙은 이미 단일 모드(스킬 /test-agent, /feat-agent, /review-agent)에서 적용 중이다.
  이 pending은 그 순서 강제를 오케스트레이터가 자동화하는 시점의 결정이다.

### 작업 위임 방식

- 서브에이전트에게 판단 체계형 하네스를 읽혀 판단시키지 않는다.
- 오케스트레이터가 하네스를 작업 카드(대상 파일, 시그니처, 제약, 통과시킬 테스트)로 컴파일해 전달한다.
- 작업 단위는 실패 테스트로 정의한다.
- 검증은 LLM 재독이 아니라 테스트 실행으로 기계화한다.

### 서브에이전트 상호작용

- 테스트 통과를 전제로 한 두 가지 방식을 조합한다.
  - 교차 리뷰: 작성자 / 리뷰어 역할 분리
  - 독립 구현 후 선택: 같은 카드를 독립 구현하고 오케스트레이터가 선택
- 자유 토론 방식은 사용하지 않는다.

### 에스컬레이션

- 같은 작업 카드에서 로컬 LLM이 2회 실패하면 리뷰 모드로 전환한다.
- 3회 실패하면 오케스트레이터가 직접 구현한다.

### decision 권한

- 서브에이전트는 decision을 만들 수 없고 질문을 오케스트레이터로 올린다.
- draft decision 작성은 오케스트레이터가 한다.
- 승격은 사람이 한다.

---

## 보류 이유

- 로컬 LLM 스택과 모델 수준이 미정이다.
  작업 카드의 크기(함수 단위 / 클래스 단위)가 모델 능력에 따라 달라진다.
- 사용 여부 자체가 사용자와 상황에 따른 조건부다.

---

## 재검토 신호 (활성화 조건)

- 사용자가 서브에이전트 사용을 결정한다.
- 로컬 LLM 스택이 확정된다.
- 단일 모델 작업의 토큰 비용이 부담될 만큼 작업량이 커진다.
