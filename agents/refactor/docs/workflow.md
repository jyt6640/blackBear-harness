# Refactor Agent Workflow

> 이 문서는 공유 정본의 실행 관점 요약이다.
> [docs](../../../docs)의 정본, decisions와 충돌하면 정본이 우선한다.


Refactor Agent의 workflow는 public behavior를 유지한 채 이름, 책임, 구조를 더 명확하게 만드는 절차다.
기능 구현, 버그 수정, 테스트 기대값 변경과 섞지 않는다.

---

## 시작 순서

1. `agents/refactor/scripts/enforce-workflow.sh <작업명>`을 실행한다.
2. 리팩터링 작업 카드 또는 Review 반려 항목을 읽는다.
3. 현재 통과 중인 테스트와 검증 명령을 확인한다.
4. 리팩터링 전 baseline 테스트를 실행한다.
5. 하나의 구조 개선 목표만 선택한다.

baseline 테스트가 깨져 있으면 리팩터링을 시작하지 않는다.
먼저 오케스트레이터에게 현재 상태를 보고한다.

---

## 리팩터링 순서

1. 이름 개선
2. 메서드 책임 분리
3. 객체 책임 이동
4. 패키지 위치 조정
5. 중복 또는 공통 흐름 정리

이름을 먼저 본다.
이름이 명확해지면 책임 문제가 드러나고, 책임 문제가 드러난 뒤에만 구조를 이동한다.

---

## 방식

- 하나의 리팩터링은 하나의 구조 개선으로 설명 가능해야 한다.
- public API와 외부 관찰 가능한 행위를 변경하지 않는다.
- 테스트 기대값을 바꾸지 않는다.
- 새로운 기능 요구가 드러나면 리팩터링을 중단하고 Test 단계로 되돌린다.
- 공통화는 두 번째 사용처나 정책 증가처럼 필요성이 드러난 뒤 진행한다.
- `validateAndUpdateAndSave`처럼 여러 책임이 섞인 이름은 분리 신호로 본다.
- getter를 꺼내 외부에서 판단하는 흐름은 Domain / Policy / Validator 책임 이동 후보로 본다.

---

## 검증 방식

1. 변경 전 테스트 명령을 기록한다.
2. 작은 변경을 수행한다.
3. 동일한 테스트 명령을 다시 실행한다.
4. 실패하면 행위 변경인지, 테스트가 구현 세부사항에 과하게 묶였는지 먼저 확인한다.
5. 행위 변경 없이는 목표를 달성할 수 없으면 중단한다.

리팩터링은 테스트가 통과하는 상태를 유지하며 진행한다.
대규모 변경 후 한 번에 검증하지 않는다.

---

## 커밋 컨벤션

리팩터링 커밋은 행위 변경 없이 하나의 구조 개선만 포함한다.

좋은 예시:

    refactor(member): 회원 생성 정적 팩터리 분리
    refactor(order): 주문 취소 검증 책임 이동

지양:

    refactor: 전체 정리
    fix: 리뷰 반영

---

## 보고서 작성

`next-step/work/<작업명>/03-refactor-report.md` 또는 별도 리팩터링 작업의 `02-green-implementation-report.md`에 아래를 기록한다.

- 리팩터링 목표
- 변경한 이름, 책임, 패키지
- 행위 보존을 확인한 테스트 명령
- 변경하지 않은 행위
- 남은 구조 신호

보고서가 없으면 Review Agent가 행위 보존 여부를 판단할 수 없다.
